## 2026-08-21 — новый диспетчер способностей билдеров + закрытие старой дыры в прайсинге

**Контекст:** добавлен универсальный диспетчер для WordPress Abilities API
(`wp-abilities/v1`) — 3 фиксированные функции вместо одной на каждую
способность каждого билдера (Bricks регистрирует ~100-140 способностей
при включённом AI; другие билдеры по мере принятия того же ядра API
добавят свои — 10-15 билдеров × ~100-145 способностей каждый раздуло бы
это приложение до 2000+ инструментов). Прямое подтверждение директивы
пользователя: "2 — деструктивные способности требовали дополнительного
подтверждения" — реализовано через `action_type="destructive"`, который
включает встроенный 2-шаговый confirm-гейт платформы.

**Три новые функции и цены (шкала `{0,8,16,20,40,60}` из `PRICING_POLICY.md`):**

| Функция | action_type | Цена | Обоснование |
|---|---|---|---|
| `describe_builder_ability` | read | 8 | GET схемы одной способности — простое чтение состояния, как `check_builder_support` |
| `call_builder_ability` | write | 16 | Запуск ЛЮБОЙ НЕ-деструктивной способности — стандартное одиночное write-действие; сама функция отклоняет `destructive:true` способности с явной отсылкой к twin-функции ниже (тот же паттерн, что `update_order_status`/`update_order_status_risky`) |
| `call_builder_ability_risky` | destructive | 16 | Запуск ТОЛЬКО `destructive:true` способностей, с автоматическим 2-шаговым подтверждением платформы — та же цена, что и write-twin (прецедент `update_order_status_risky` в этом же приложении) |

**Попутно найдена и исправлена старая дыра:** `list_wp_abilities`
(добавлена ранее, не в этой сессии) не имела цены в `tool-prices.json`
вообще — обнаружено тестом `test_pricing_map.py` при деплое сегодняшних
изменений. `action_type="read"` → цена 8, тот же уровень, что
`list_users`/`list_themes`. Это не связано с сегодняшней новой
функциональностью, но раз тест это выявил — исправлено в рамках этого же
хода по правилу "никогда не деплоить с известной дырой в прайсинге".

**Метод применения — `developer.update_pricing`, приложение уже было
`active` (опубликовано):**
1. `developer.suspend_app("wordpress-hub")` — обязательный шаг для
   активного приложения перед изменением цены (см. канонический
   `PRICING_POLICY.md` §3).
2. `developer.update_pricing(app_id="wordpress-hub", pricing_model="per_action",
   pricing_config={"tool_prices": {...264 функции...}, "free_tools": [...5...],
   "monthly_price": 0}, revenue_split_dev=95)` — `pricing_config` передан
   как настоящий вложенный объект (НЕ строка — первая попытка поймала
   `dict_type` ошибку Pydantic ровно как предупреждает канон),
   `revenue_split_dev=95` (partner-тир этого разработчика, подтверждён
   прецедентами Asana/MuleSoft Connector) передан явным параметром.
3. `developer.deploy_app("wordpress-hub")` — синхронизация кода и
   манифеста после применения цены.
4. `developer.submit_for_review("wordpress-hub")` — вернуть приложение
   из `suspended` обратно в публичный листинг Marketplace. Все 4
   платформенные проверки прошли (`git_url_https`, `display_name_set`,
   `description_set`, `last_deploy_succeeded`) → `pending_review`.

**Технический инцидент по пути (см. также задачу в трекере Imperal Cloud,
заведена этим же ходом):**
- Локальный `.git` этого приложения оказался повреждён — один packfile
  обрезан (`far too short to be a packfile`), из-за чего ни `git commit`,
  ни `git fetch` не проходили. Обойдено через свежий клон из GitHub во
  временную папку, ручной перенос изменённых файлов, коммит и push
  оттуда (`98c34dc`, затем `4052899` с исправлением цены).
- `imperal build` (CLI) НЕ читает `tool-prices.json` в
  `imperal.json["pricing"]["tool_prices"]` автоматически — это поле
  нужно синхронизировать вручную (или через отдельный скрипт) после
  каждого изменения `tool-prices.json`, иначе `test_pricing_map.py`
  ловит рассинхрон между манифестом и файлом цен.

**Полная карта цен (264/264 функции)** — источник истины:
`tool-prices.json` в корне приложения, зеркалировано в
`imperal.json["pricing"]["tool_prices"]`.
