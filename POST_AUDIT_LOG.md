## 2026-08-19 — Сквозной пост-аудит + исправление окружения тестов

**Что проверялось:** py_compile всех 50 модулей; количество `@chat.function`
(260, совпадает с манифестом, крупнейшее приложение в портфеле); все 23
`action_type="destructive"` функции; все 8 функций с именами
`delete_*`/`purge_*`, классифицированными `write` (не `destructive`), на
правдоподобность классификации; две функции с `action_type=None`
(`skeleton_refresh_sites_overview`, `skeleton_alert_sites_overview`) — не
дефект, это внутренние skeleton/ambient-context хелперы фреймворка, не
вызываются пользователем напрямую, поэтому `action_type` им не нужен;
систематическая (не выборочная) проверка double-prompt антипаттерна:
скрипт распарсил все Python-классы во всех `*.py` на предмет буквального
поля `confirm*: bool`, затем сверил каждый найденный такой класс с тем,
использует ли его хоть одна `@chat.function`; отдельно прямой
`grep -n "confirm.*:\s*bool"` по всем файлам как перекрёстная проверка;
полный прогон тестового набора (66 файлов, 864 теста).

**Найдена и исправлена платформенная (не кодовая) проблема:** `.venv/`
приложения был битым/неполным — содержал только `pyvenv.cfg`, без
`bin/`/`lib/`, то есть `pytest` физически не мог быть запущен через
`.venv/bin/pytest` (как во всех остальных приложениях). Причина не
установлена (возможно прерванная установка). Пересобрала venv с нуля:
`python3 -m venv .venv`, `pip install -r requirements.txt pytest
pytest-asyncio`. После пересборки все тесты запустились и прошли.

### Находки

1. **Окружение (не код) было неисправно: пустой `.venv`.** Исправлено
   пересборкой. Без этого исправления пост-аудит тестов для этого
   приложения был бы невозможен — задокументировано на случай, если та же
   картина повторится при следующем пост-аудите (тогда это уже системная,
   а не разовая проблема окружения).
2. **Double-prompt антипаттерн не найден.** Систематическая проверка (не
   выборочная) — ни один Python-класс во всём приложении не содержит
   буквального поля `confirm*: bool`. 21 файл содержит текстовое слово
   "confirm" — всё это docstring/комментарии о поведении (например, при
   двухфазном подтверждении preview→apply у bulk-операций, которое САМО
   ЯВЛЯЕТСЯ корректным платформенным паттерном, а не hand-rolled confirm
   полем).
3. **Все 23 `destructive`-функции и все 8 `write`-классифицированных
   delete/purge функций правдоподобны.** `write`-делеты (`delete_redirect`,
   `delete_404_hit`, `delete_post_meta`, `delete_user_meta`,
   `delete_term_meta`, `delete_transient`, `delete_cron_event`,
   `purge_cache`) все касаются низкорисковых/легко воссоздаваемых
   метаданных (кэш, лог 404, транзиенты, cron-события, custom-meta ключи)
   — не пользовательский контент/бизнес-данные, поэтому `write` разумен, в
   отличие от найденного ранее в этой серии аудитов бага в Trello
   Connector (`delete_board`).
4. Полный тестовый набор (864 теста, 66 файлов) — все прошли за 1.74с
   после пересборки venv.

Пересобран `.venv` (окружение, не код приложения). Код приложения не
